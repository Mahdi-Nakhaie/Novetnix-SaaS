# DR-10 — گزارش آزمون و ممیزی دریچه

تاریخ: ۲۰۲۶-۱۰-۲۰
مبنای شروع: کامیت `91c5a94`

## نتیجه کلی: FAIL برای پذیرش کامل

آزمون‌های اجراشده پس از اصلاح موفق‌اند، اما پذیرش کامل هنوز احراز نشده است: آزمون بصری موبایل، تبلت و دسکتاپ، کار واقعی با صفحه‌کلید و مرورگر، پایگاه داده MySQL و اجرای محصول از طریق رانر عملیاتی انجام نشده‌اند. این موارد **NOT TESTED** هستند؛ نتیجه FAIL به معنای وجود خطای تأییدشدهٔ باز در مسیرهای آزموده‌شده نیست.

- ۳۷ آزمون دریچه: موفق.
- ۴۵ آزمون مجاور: ۴۴ موفق، یک آزمون اختیاری شبکه‌ای اجرا نشد.
- ۶ آزمون بدون مرورگر رابط دریچه: موفق؛ شامل DOM شبیه‌سازی‌شده و قراردادهای CSS.
- مجموعهٔ رابط میزکار بدون مرورگر: موفق؛ خروجی ابزار تعداد مستقل تست‌ها را اعلام نمی‌کند و در جمع عددی شمرده نشده است.
- جمع عددی: **۸۷ آزمون موفق، یک مورد skipped**، به‌علاوه مجموعهٔ رابط میزکار.
- بررسی نحو سه فایل PHP تغییرکرده: موفق.

موفقیت اسکریپت‌های بررسی CSS یا متن کد، به‌عنوان PASS تجربهٔ واقعی رابط یا تضمین امنیت محصول محسوب نشده است.

## محیط و روش

آزمون‌های HTTP با PHP واقعی، سشن واقعی برنامه، SQLite موقت و کاربران ساختگی روی محیط آزمایشی جدا در سرور ثبت‌شده اجرا شدند. ارتباط SMS در fixture جایگزین شده است. آزمون‌های هم‌زمانی با پردازش‌های مستقل PHP و پایگاه دادهٔ همین fixture اجرا شدند؛ برای ساخت محصول دو درخواست موازی محدود استفاده شد، نه آزمون بار.

فایل Python تولیدشده از تصمیم‌های سناریو واقعاً در پوشهٔ موقت اجرا شد. خروج موفق، خروج ناموفق پس از تغییر عمدی الگوریتم، و محتوای `product-results.json` بررسی شدند. این اجرا، آزمون رانر عملیاتی یا ایزولیشن اجرای کد کاربر محسوب نمی‌شود.

هیچ مرورگر، اتوماسیون مرورگر یا سرور پیش‌نمایش دائمی اجرا نشد. سرویس HTTP موقت آزمون با پایان مجموعه متوقف شد. هیچ دادهٔ واقعی کاربر بررسی و هیچ نسخه‌ای روی سایت اصلی مستقر نشد.

## ایرادهای پیدا‌شده و شدت

### DR10-01 — متوسط — اصلاح‌شده

**عنوان:** ساخت چند پروژه با تکرار همان درخواست ساخت خروجی.

**بازتولید واقعی:** دو POST به `darycheh/build` با همان کاربر، تلاش، revision و request_key، پیش از اصلاح دو project_id متفاوت ایجاد کردند. آزمون `test_audit_duplicate_product_request_is_atomic_and_idempotent` واقعاً FAIL شد.

**اثر:** ارسال مجدد شبکه یا دو بار ارسال فرم می‌توانست پروژهٔ اضافی بسازد و سهمیهٔ بیست پروژه را بی‌دلیل مصرف کند. دسترسی به دادهٔ کاربر دیگر در این بازتولید مشاهده نشد.

**اصلاح:**

- جدول افزایشی `darycheh_product_requests` با کلید یکتای کاربر/درخواست و ارجاع به تلاش و پروژه اضافه شد.
- ساخت محصول، ایجاد میزکار و ثبت رسید در یک تراکنش و زیر قفل همان کاربر قرار گرفت.
- تکرار همان درخواست همان نتیجه را برمی‌گرداند؛ استفاده از کلید قبلی با id/revision متفاوت تعارض ۴۰۹ می‌دهد.
- ایجاد مستقل با request_key تازه همچنان مطابق قرارداد قبلی ممکن است.
- `ws_create` تراکنشی را که خودش آغاز نکرده، commit یا rollback نمی‌کند؛ مالک تراکنش بیرونی مسئول نتیجه است.
- شکست ساختگی ثبت رسید ثابت کرد که هیچ پروژهٔ یتیم یا رسید ناقص باقی نمی‌ماند.

**تأیید اصلاح:** آزمون درخواست تکراری، تعارض fingerprint، جداسازی کاربران، دو درخواست هم‌زمان و rollback همگی پس از اصلاح موفق شدند.

در دامنهٔ اجراشده، ایراد بحرانی یا شدید بازتولید نشد؛ این جمله جایگزین آزمون موارد NOT TESTED یا تضمین امنیت کامل نیست.
