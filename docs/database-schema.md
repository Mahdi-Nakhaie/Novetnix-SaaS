# Core Schema MVP: User، Course، Lesson و Progress

این سند طرح SQL سروری در `src/schema.sqlite.sql` و `src/schema.mysql.sql` را شرح می‌دهد، بدون جایگزینی کاتالوگ محتوای فعلی در `src/data.php` و `tools/catalog.py`. برنامه همچنان دوره‌ها را از کاتالوگ ثابت می‌خواند؛ جدول‌های دوره، درس و پیشرفت درس دادهٔ اولیه/seed یا مسیر مدیریت/ثبت پیشرفت ندارند. انتشار GitHub Pages پایگاه‌دادهٔ سروری ندارد.

## `users` — هویت حساب

- **هدف:** حساب ورود کاربر. جدول موجود و جریان احراز هویت فعلی بدون بازتعریف حفظ شده‌اند.
- **فیلدها:** `id`, `phone`, `name`, `password_hash`, `role`, `created_at`؛ مقدار `phone` شناسهٔ احراز هویت است و ضروری/یکتاست. `created_at` در زمان درج مقداردهی می‌شود؛ `updated_at` در User فعلی وجود ندارد و افزودن آن به دیتابیس‌های پرشده نیازمند migration جداگانه است، نه بازسازی جدول.
- **PK:** `id` خودافزا. **Unique:** `phone`. **FK:** ندارد؛ اشتراک‌ها و سایر موجودیت‌های موجود از `user_id` به این جدول اشاره می‌کنند. **Index:** ایندکس یکتای `phone` برای lookup ورود؛ PK روی `id`.
- **رابطهٔ آینده:** User با `id` ثابت می‌تواند به مدل‌های Plan/Subscription/Payment مرتبط شود؛ `subscriptions` از قبل وجود دارد و در این مرحله تغییر نکرده است.

## `courses` — دورهٔ قابل‌شناسایی

- **هدف:** پایهٔ ذخیرهٔ دوره با هویت پایدار مستقل از ترتیب آرایهٔ کاتالوگ.
- **فیلدها:** `id`, `slug` (شناسهٔ متنی پایدار سازگار با کلیدهای کاتالوگ فعلی)، `title`, `description`, `status` (پیش‌فرض `draft`، مقادیر `draft`/`published`)، `created_at`, `updated_at`. توضیحات/عنوان اجباری‌اند؛ timestampها هنگام درج مقداردهی می‌شوند و هنگام ویرایش آینده باید صریحاً به‌روزرسانی شوند.
- **PK:** `id` خودافزا. **Unique:** `slug`. **FK:** ندارد. **Index:** PK و ایندکس یکتای slug برای lookup؛ ایندکس دیگری در این مرحله لازم نیست.
- **رابطه:** هر Course می‌تواند چند Lesson داشته باشد. رکوردهای `enrollments.course_slug` فعلی هنوز FK به این جدول ندارند؛ تغییر آن خارج از این مرحله است.

## `lessons` — محتوای مرتب یک دوره

- **هدف:** تعریف عنوان، محتوای متنی و ترتیب درس درون یک دوره، متناسب با متن بخش‌های فعلی کاتالوگ.
- **فیلدها:** `id`, `course_id`, `title`, `content` (متن درس)، `position` (عدد مثبت، از ۱)، `created_at`, `updated_at`. عنوان و محتوا اجباری‌اند؛ timestampهای ویرایش باید توسط منطق ویرایش آینده مدیریت شوند.
- **PK:** `id` خودافزا. **FK:** `course_id NOT NULL` به `courses(id)`؛ به User اشاره نمی‌کند. حذف دوره‌ای که درس دارد به‌صورت پیش‌فرض محدود است (بدون cascade).
- **Unique و Index:** `UNIQUE(course_id, position)` ترتیب تکراری یک Course را منع می‌کند و همان ایندکس مرکب برای جست‌وجوی `WHERE course_id = ? ORDER BY position` کافی است؛ ایندکس تکراری جداگانه لازم نیست. دوره‌های متفاوت مجازند position یکسان داشته باشند.
- **رابطه:** Course 1 → N Lesson؛ هر Lesson دقیقاً یک Course معتبر دارد.

## `lesson_progress` — پیشرفت کاربر در درس

- **هدف:** یک رکورد وضعیت برای هر ترکیب User و Lesson؛ رابطهٔ `User 1:N lesson_progress N:1 Lesson`. این جدول از `challenge_progress` موجود مستقل است و Course از طریق `lessons.course_id` خوانده می‌شود؛ ستون `course_id` در پیشرفت تکرار نشده است.
- **فیلدها:** `id`, `user_id`, `lesson_id`, `status` (اجباری، پیش‌فرض `started`؛ مقدار دیگر `completed`)، `completed_at` (قابل‌تهی فقط تا قبل از تکمیل)، `created_at`, `updated_at`. `completed_at` برای وضعیت `completed` اجباری و برای `started` ممنوع است. `updated_at` هنگام درج مقدار اولیه می‌گیرد و در منطق ویرایش آینده باید صریحاً تغییر کند. درصد پیشرفت اضافه نشده چون در این مرحله فقط شروع/اتمام مدل شده است.
- **PK:** `id` خودافزا. **FK:** `user_id NOT NULL → users(id)` و `lesson_id NOT NULL → lessons(id)`؛ حذف والد دارای رکورد پیشرفت به‌طور پیش‌فرض محدود است تا رکورد orphan ایجاد نشود. FK مستقیمی به Course وجود ندارد.
- **Unique و Index:** `UNIQUE(user_id, lesson_id)` هم از ثبت تکراری جلوگیری می‌کند و هم ایندکس پرس‌وجوی پیشرفت یک User است. `idx_lesson_progress_lesson` روی `lesson_id` برای جست‌وجوی پیشرفت‌های یک درس و FK معکوس وجود دارد؛ ایندکس مستقل روی `user_id` لازم نیست.

## سازگاری و راه‌اندازی

- **SQLite:** `src/app.php` در آغاز اتصال `PRAGMA foreign_keys=ON` اجرا می‌کند تا قید FK واقعاً اعمال شود. **MySQL:** قیود FK و ایندکس مرکب در `src/schema.mysql.sql` آمده‌اند؛ بررسی عملی روی سرور MySQL هنوز انجام نشده است.
- برنامه در `db()` اسکیما را با `CREATE TABLE IF NOT EXISTS` اجرا می‌کند؛ این کار جدول `lesson_progress` را در کنار جدول‌های موجود بدون بازسازی User/Course/Lesson ایجاد می‌کند. این روش migration نسخه‌دار عمومی نیست: اگر جدول هم‌نام با تعریف ناسازگار از قبل وجود داشته باشد، تعریف آن به‌روزرسانی نمی‌شود. پیش از استقرار در محیط واقعی وضعیت جدول‌ها و نسخهٔ MySQL (برای اجرای CHECK نیازمند MySQL 8.0.16 یا بالاتر) را بررسی و نسخهٔ پشتیبان تهیه کنید. برای کارهای بعدی از migration نسخه‌دار و تدریجی استفاده شود.
- به‌جز `lesson_progress` هیچ Entity دیگری در این مرحله ایجاد یا تغییر نشده است؛ `challenge_progress` موجود دست‌نخورده مانده است. PostgreSQL/MSSQL هنوز driver/schema اجرایی ندارند؛ نام‌گذاری و روابط مستقل از موتورند ولی DDL برای هر موتور باید جداگانه پیاده‌سازی و آزمون شود.
- آزمون `python3 -m unittest tools/test_core_schema.py` روی SQLite حافظه‌ای از دیتابیس خالی و دیتابیس قبلی، یکتایی `(user_id, lesson_id)`، FKها، منع حذف والد با رکورد وابسته، وضعیت/تاریخ تکمیل و ایندکس‌ها را بررسی می‌کند. اجرای PHP و MySQL به محیطی با آن ابزارها نیاز دارد.
