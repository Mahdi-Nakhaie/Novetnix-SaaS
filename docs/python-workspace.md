# زیرساخت مشترک میزکار پایتون

## وضعیت تحویل و ممیزی معماری

این تغییر، پیاده‌سازی کد و آزمون‌های محلی است، نه اعلام آماده‌بودن سرویس عملیاتی. آزمون‌های HTTP با PHP 8.4 و اتصال واقعی Hub اجرا شده‌اند؛ Docker، gVisor و سرور SSH ثبت‌شده در دسترس نیستند. هیچ سرویس پولی، تصویر اجرایی یا زیرساخت تولیدی فعال نشده است.

معماری موجود حفظ شده است:

- `public/index.php` ورودی PHP؛ `src/app.php` منطق و POST؛ `src/router.php` مسیریابی؛ `src/views.php` نمایش پنل.
- احراز هویت session، کاربران تأییدشده، نقش مدیر، CSRF و PDO موجود دوباره استفاده می‌شوند.
- پایگاه داده SQLite یا MySQL، جدول `projects` و رابطه مالکیت `user_id` موجود حفظ شده‌اند. دوره، درس و ثبت‌نام نیز همان سیستم فعلی هستند.
- محتوای کاتالوگ موجود عمدتاً ثابت است. دموی HTML/worker مبتنی بر Pyodide و localStorage، سرویس اجرای سمت سرور یا ذخیره خصوصی حساب نیست.
- انتشار HTML روی GitHub Pages به‌تنهایی PHP یا runner را فعال نمی‌کند. وضعیت واقعی میزبان تولید از این محیط قابل تأیید نیست.
- هیچ داده واقعی دیابت/قیمت خانه یا خروجی آموزشی ساختگی اضافه نشده؛ مدیر باید محتوای مجاز و واقعی را بارگذاری کند.

## معماری پیاده‌سازی‌شده

مسیرهای مشترک:

- `/dashboard/workspace`: ایجاد، فهرست و بازیابی پروژه خصوصی.
- `/dashboard/workspace/{id}`: ویرایشگر مشترک.
- `/dashboard/workspace-templates`: مدیریت الگو در پنل مدیر موجود.
- `/workspace/*`: API احراز هویت‌شده با کنترل مالکیت و CSRF برای تغییرات.

سه جدول افزوده شده‌اند:

1. `workspace_templates`: عنوان، دستورالعمل، انتشار، ارتباط با دوره/درس/کاتالوگ، فایل‌های اولیه و revision.
2. `project_workspaces`: رابطه یک‌به‌یک با `projects`، فایل‌های مستقل کاربر، سهمیه، revision و حذف نرم.
3. `workspace_runs`: snapshot تغییرناپذیر درخواست، کلید تکرارناپذیری، شناسه remote و نتیجه اجرا.

فایل‌های عادی و قدیمی میزکار به‌صورت manifest با محتوای base64 در پایگاه داده خصوصی ذخیره می‌شوند؛ نه در public. **دیتاست‌های واردشده از Hub روی دیسک خصوصی‌اند و فقط مرجع و فراداده‌شان در DB ذخیره می‌شود.** snapshot اجرا برای دیتاست نیز مرجع است و محتوا فقط هنگام ارسال به runner خوانده می‌شود. ورودی صف runner روی دیسک خصوصی spool می‌شود؛ فایل‌های دیتاست از نتایج ذخیره‌شده DB حذف می‌شوند. base64 رمزنگاری نیست؛ رمزنگاری دیسک، مجوز دیتابیس و پشتیبان امن وظیفه استقرار است. مسیر دانلود فقط پس از احراز مالکیت، با attachment و nosniff پاسخ می‌دهد. درخواست‌های SQL پارامتری‌اند؛ متن فایل/خروجی با textContent و escape نمایش داده می‌شود.

شروع الگو یک کپی مستقل می‌سازد و درخواست تکراری همان پروژه را باز می‌کند. به‌روزرسانی فایل‌های الگو فایل کاربر را عوض نمی‌کند. توضیحات تمرین از نسخه فعلی الگو نمایش داده می‌شوند. پروژه‌های مستقل از شناسه کاتالوگ منفی استفاده می‌کنند تا هویت موجود projects حفظ شود. پروژه کاتالوگ با الگوی منتشرشده به همین میزکار متصل می‌شود؛ پروژه قدیمی نیز از فهرست میزکار قابل اتصال است.

ذخیره با تراکنش، قفل مالک برای سهمیه و compare-and-swap revision انجام می‌شود. ذخیره هم‌زمان قدیمی 409 می‌گیرد. خروجی اجرا فقط با اقدام صریح و روی همان revision اعمال می‌شود. حذف نرم قابل بازیابی است؛ سطل بازیافت همچنان سهمیه مصرف می‌کند.

## فایل، دیتاست و محدودیت‌ها

- هر فایل: 1 MiB؛ هر پروژه: 5 MiB؛ هر حساب: 20 MiB؛ حداکثر 20 پروژه و 100 ورودی فایل/پوشه در هر پروژه.
- فرمت‌ها: py، txt، csv، json، md، png، joblib، pkl، npy، npz. پذیرفتن پسوند به معنی قابل‌اعتمادبودن محتوا نیست. سرور برنامه مدل pickle/joblib را deserialize نمی‌کند؛ چنین فایل‌هایی تنها در sandbox قابل استفاده‌اند.
- نام‌ها و مسیرها محدود به نویسه‌های ASCII مجازند؛ مسیر مطلق، backslash، بخش مخفی، dot traversal و برخورد فایل/والد رد می‌شوند.
- ZIP هرگز روی filesystem برنامه extract نمی‌شود؛ ورودی‌ها با تعداد/اندازه محدود مستقیماً خوانده می‌شوند. مسیر مخرب، لینک، ورودی ویژه، رمزگذاری و تکرار رد می‌شوند.
- ZIP به افزونه PHP ZipArchive نیاز دارد. آپلود عادی فایل جایگزین است.
- URL دلخواه کاربر پشتیبانی نمی‌شود. بخش Datasets فقط API رسمی Hub و فایل‌های نسخه ثابت در دامنه مجاز را دریافت می‌کند؛ جزئیات محدودیت‌ها پایین آمده است. آپلود مستقیم نیز حفظ شده است.
- سقف درخواست برنامه 8 MiB است؛ وب‌سرور و PHP نیز باید سقف متناسب داشته باشند. سربار multipart و base64 را لحاظ کنید.
- تاریخچه اجرا حداکثر 100 رکورد و بودجه 64 MiB برای هر مالک دارد؛ رزرو 16 MiB برای اجرای جدید لحاظ می‌شود. پاک‌سازی دائمی و تاریخچه کامل فایل رابط مدیریتی ندارند؛ پیش از ظرفیت بالا سیاست نگهداری لازم است.

## سرویس اجرای مستقل

`services/python-runner/server.py` یک API استاندارد Python و صف ماندگار SQLite دارد. PHP فقط snapshot را به مقصد HTTPS ثابت پیکربندی‌شده می‌فرستد؛ کد دانشجو در PHP یا فرایند میزبان اجرا نمی‌شود. API loopback runner پشت reverse proxy TLS و دسترسی شبکه محدود قرار می‌گیرد. توکن فقط توسط اپراتور تنظیم می‌شود و در مرورگر قرار نمی‌گیرد.

هر اجرا یک container تازه با Docker و **gVisor/runsc اجباری** می‌گیرد. نبود runsc یا cgroups v2 مانع شروع سرویس است؛ fallback به اجرای عادی وجود ندارد.

مرزهای اجرا:

- تصویر بررسی‌شده و pin شده با digest؛ pull خودکار ممنوع.
- UID/GID غیرریشه 65532، root filesystem فقط‌خواندنی، تمام capabilityها حذف، no-new-privileges.
- بدون network و host mount؛ متغیرهای حساس میزبان به child منتقل نمی‌شوند.
- حافظه 512 MiB، بدون swap اضافی، یک CPU، حداکثر 64 پردازه و ulimit پردازنده 10 ثانیه.
- workspace و tmp هرکدام tmpfs محدود 16 MiB با noexec/nosuid/nodev؛ فایل خروجی حداکثر 1 MiB.
- مهلت child برابر 15 ثانیه؛ deadline بیرونی 30 ثانیه؛ startup/cleanup نیز timeout مستقل دارند.
- خروجی child مجموعاً حدود 128 KiB؛ هر جریان نمایشی حداکثر 64 KiB؛ پاسخ بیرونی حداکثر 8 MiB.
- دو worker؛ یک اجرای فعال برای هر مالک؛ حداکثر 32 کار فعال و 10 درخواست در دقیقه برای هر مالک.
- صف حداکثر 500 رکورد دارد؛ رکوردهای پایان‌یافته قدیمی‌تر از 24 ساعت هنگام ارسال جدید پاک می‌شوند، نه با تضمین حذف دقیق در ساعت مشخص.

یک lock انحصاری مانع چند instance برای همان DB می‌شود. بازیابی startup اجراهای قطع‌شده را متوقف و infrastructure_error می‌کند. شکست یا عدم قطعیت پاک‌سازی/راه‌اندازی container سرویس را متوقف از پذیرش می‌کند و نیازمند بررسی اپراتور است. شناسه ثابت درخواست و fingerprint از اجرای دوباره snapshot در retry جلوگیری می‌کنند. وضعیت‌های برنامه، وابستگی، timeout، حافظه، CPU، خروجی، artifact، لغو و زیرساخت جدا هستند.

امنیت sandbox مطلق نیست؛ runtime میزبان و kernel باید به‌روز، میزبان runner اختصاصی و فاقد داده حساس برنامه باشد. Docker socket دسترسی بسیار قدرتمند است و نباید داخل وب‌اپ یا container دانشجو قرار بگیرد. سرویس صرفاً به نام مجوزهای container نباید تولیدی تلقی شود؛ آزمون واقعی ایزولاسیون و بازبینی عملیاتی الزامی است.

## وابستگی‌ها و یادگیری ماشین

Python 3.12.x و پروفایل ثابت:

| بسته | نسخه |
|---|---|
| numpy | 2.2.3 |
| pandas | 2.2.3 |
| scipy | 1.15.2 |
| scikit-learn | 1.6.1 |
| matplotlib | 3.10.1 |
| joblib | 1.4.2 |

`requirements.txt` فقط نام و نسخه دقیق از همین فهرست را می‌پذیرد. نصب اینترنتی حین اجرا، URL، index دلخواه، نسخه باز، GPU، torch و کتابخانه دلخواه پشتیبانی نمی‌شوند. بسته‌های مجاز هنگام ساخت تصویر نصب می‌شوند، نه در درخواست PHP. startup probe نسخه واقعی Python و بسته‌ها را در خود sandbox بررسی می‌کند و API سلامت همان نتیجه را نمایش می‌دهد.

Dockerfile منبع ارائه شده است؛ تصویر ساخته نشده. وابستگی‌های مستقیم pin شده‌اند اما lock هش‌دار کامل وابستگی‌های گذرا فراهم نشده؛ اپراتور باید تصویر نهایی، وابستگی‌های گذرا و آسیب‌پذیری‌ها را بررسی و digest تأییدشده را نگهداری کند.

پشتیبانی CSV، آموزش sklearn و PNG Matplotlib در کد/آزمون sandbox پیش‌بینی شده، اما بدون اجرای آزمون روی سرور ادعای عملکرد واقعی نداریم. ورودی تعاملی stdin و notebook پشتیبانی نمی‌شوند.

## راه‌اندازی واقعی

1. پشتیبان پایگاه داده موجود بگیرید و بازیابی آن را در staging تمرین کنید. برای SQLite نوشتن هم‌زمان هنگام کپی خام مجاز نیست؛ از backup سازگار SQLite استفاده کنید.
2. PHP 8.2+ با PDO موتور فعلی، mbstring، curl و در صورت نیاز zip فراهم کنید. document root همان public باشد؛ DB و تنظیمات خارج از دسترسی عمومی بمانند.
3. schemaهای موجود به‌صورت CREATE IF NOT EXISTS سه جدول را اضافه می‌کنند؛ ستون یا داده قدیمی حذف نمی‌شود. پیش از production روی کپی دیتابیس بررسی کنید. rollback برنامه داده جدید را حذف نمی‌کند؛ جداول را برای برگشت احتمالی حفظ کنید.
4. روی **سرور ثبت‌شده و مجاز پروژه** یک میزبان Linux اختصاصی runner با Docker، runsc، cgroups v2، Python 3.12 و فضای دیسک پایدار فراهم کنید. در این محیط هیچ build سنگینی انجام نشد.
5. اپراتور base image Python 3.12 تأییدشده با sha256 را تهیه کند؛ Dockerfile را با build arg به نام PYTHON_BASE روی سرور بسازد، اسکن کند و digest تصویر نهایی را ثبت کند. build فقط در maintenance و با مجوز شبکه مخازن مورد اعتماد انجام شود.
6. یک دایرکتوری خصوصی پایدار برای DB صف و lock، مالک سرویس و مجوزهای حداقلی تعیین کنید. RUNNER_DB مسیر فایل صف، RUNNER_IMAGE تصویر digest-pinned، RUNNER_TOKEN راز تصادفی حداقل 32 نویسه و RUNNER_PORT پورت loopback هستند. مقدار راز را در Git، log، shell history یا گزارش قرار ندهید.
7. runner را با process manager مانند systemd اجرا کنید؛ دستور اجرا `python3 services/python-runner/server.py` است. یک instance برای هر DB، restart محدود، توقف کنترل‌شده و alert خطای زیرساخت لازم است. فایل نمونه unit خودکار نصب نشده است.
8. reverse proxy با TLS معتبر، سقف بدنه و timeout مناسب و firewall محدود به سرور PHP تنظیم کنید. endpoint داخلی runner نباید سرویس عمومی بدون محدودیت شبکه باشد. redirect و HTTP در client PHP پذیرفته نمی‌شوند.
9. در تنظیمات امن موجود برنامه PYTHON_RUNNER_URL و PYTHON_RUNNER_TOKEN را تنظیم کنید؛ تنها نام تنظیمات در مخزن آمده، نه مقدار واقعی.
10. آزمون‌های PHP/HTTP و sandbox زیر را روی staging مجاز اجرا کنید؛ سپس از پنل مدیر یک الگو با main.py، requirements.txt و CSV واقعی منتشر و از حساب دانشجو شروع کنید. به‌روزرسانی الگو، retry، ذخیره مجدد، دو حساب و بازیابی را بررسی کنید.
11. قبل از ترافیک واقعی monitoring صف، خطای cleanup، ظرفیت DB، انقضای داده، backup هر دو DB، چرخش راز و patching را عملیاتی کنید. هزینه شامل میزبان runner، RAM/CPU، دیسک و backup و نگهداری است؛ قیمت یا سرویس خاصی خریداری نشده است.

## آزمون و شواهد پذیرش

آزمون‌های سبک:

```sh
python3 -m unittest discover -s tools -p 'test_*.py' -q
node --check public/assets/workspace.js
git diff --check
```

ماژول HTTP موجود با PHP نصب‌شده اجرا می‌شود. آزمون sandbox فقط روی staging مجاز و با تصویر آماده:

```sh
NOVENTIX_SANDBOX_TESTS=1 python3 -m unittest discover -s tools -p 'test_workspace.py' -v
```

RUNNER_IMAGE باید قبلاً توسط اپراتور در محیط امن تنظیم شده باشد. این فرمان آزمون‌های واقعی container را اجرا می‌کند؛ در محیط فعلی اجرا نشده است.

آزمون‌های محلی policy، صف، idempotency، لغو، سهمیه، مالکیت SQL، ماندگاری DB، جدایی الگو، revision، schema افزایشی و قواعد اتصال امنیتی را بررسی می‌کنند. بررسی منبع/SQL جای آزمون یکپارچه PHP یا اثبات sandbox را نمی‌گیرد.

| معیار | وضعیت این تحویل | شواهد / مانع |
|---|---|---|
| 1. ایجاد/ویرایش/ذخیره با حساب واردشده | PASS | آزمون واقعی PHP/HTTP و SQLite |
| 2. اجرای واقعی Python | NOT TESTED | Docker/runsc و تصویر آماده موجود نیست |
| 3. SyntaxError و خطای runtime واقعی | NOT TESTED | آزمون sandbox آماده اما اجرا نشده |
| 4. CSV و آموزش sklearn | NOT TESTED | پروفایل و آزمون ML آماده؛ runtime در دسترس نیست |
| 5. ماندگاری پس از خروج/ورود | NOT TESTED | reopen دیتابیس و auth جداگانه PASS؛ چرخه کامل logout/login میزکار آزموده نشده |
| 6. جدایی کاربران در پروژه/API | PASS | دو حساب واقعی HTTP و جدایی صف؛ ایزولاسیون filesystem sandbox جداگانه NOT TESTED است |
| 7. منع دسترسی خارج sandbox | NOT TESTED | بررسی flags PASS؛ اثبات ایزولاسیون به staging وابسته است |
| 8. اعمال واقعی منابع/زمان | NOT TESTED | محدودیت‌ها در کد؛ آزمون container اجرا نشده |
| 9. افزودن الگو توسط مدیر و اجرای دانشجو | NOT TESTED | استقلال کپی در DB PASS؛ مسیر کامل HTTP/runtime اجرا نشده |
| 10. عدم regression آزمون‌های موجود | PASS برای آزمون‌های قابل اجرا | نتیجه عددی اجرای نهایی در گزارش تحویل؛ موارد skip مستثنا هستند |

هیچ معیار end-to-end صرفاً به اتکای mock، syntax parser یا بررسی رشته‌های منبع PASS نشده است. مرورگر و بررسی بصری انجام نشده‌اند.

## اتصال Hugging Face Hub — MVP دیتاست عمومی

### مسیر و رفتار

بخش Datasets داخل همان ویرایشگر پروژه قرار دارد؛ میزکار یا موتور Python جدا ساخته نشده است. جست‌وجو، جزئیات، منبع، مجوز (یا نامشخص)، قالب، اندازه تقریبی مخزن و انتخاب فایل از PHP ارائه می‌شوند. API رسمی استفاده‌شده:

- `GET https://huggingface.co/api/datasets?search=...&limit=15&full=true`
- `GET /api/datasets/{id}?blobs=true`
- `GET /api/datasets/{id}/revision/{commit}?blobs=true`
- `GET /datasets/{id}/resolve/{commit}/{file}`

مرجع رسمی: https://huggingface.co/docs/hub/api . درخواست‌ها بدون توکن یا cookie انجام می‌شوند؛ هیچ کلید Hub لازم نیست. خصوصی، gated، disabled و وضعیت دسترسی نامشخص از نتایج عمومی حذف می‌شوند و پیش از هر دانلود دوباره بررسی می‌شوند. اندازه نمایش‌داده‌شده مجموع اندازه فایل‌های گزارش‌شده است، نه برآورد سخت‌افزار موردنیاز یا storage داخلی Hub؛ اندازه نامعلوم با null/نامشخص نمایش داده می‌شود.

فقط CSV/JSON/TXT با UTF-8 معتبر، بدون NUL و checksum معتبر پذیرفته می‌شوند. JSON نیز parse می‌شود. script، pickle، مدل اجرایی، ZIP، Parquet، فایل باینری و فایل بزرگ در این مسیر دریافت نمی‌شوند. فایل متنی اسکن ضدویروس سراسری نمی‌شود؛ محتوا در وب اجرا نمی‌شود و کاربر نباید CSV را بدون رعایت امنیت در نرم‌افزار spreadsheet باز کند. دریافت خودکار و اجرای کد دیتاست وجود ندارد.

### سقف‌ها و امنیت

- هر فایل 1 MiB؛ هر دریافت حداکثر 10 فایل و 2 MiB؛ ظرفیت موجود پروژه 5 MiB و حساب 20 MiB شامل دیتاست‌ها و رزرو دریافت فعال است.
- یک دریافت فعال برای هر حساب؛ حداکثر 100 رکورد تاریخچه دریافت برای هر حساب؛ حداکثر 30 درخواست عملیات Hub در دقیقه. جست‌وجو حداکثر 15 نتیجه دارد و pagination در MVP ندارد.
- مهلت کل دریافت 120 ثانیه، هر درخواست شبکه حداکثر 10 ثانیه و اتصال حداکثر 3 ثانیه؛ اندازه پاسخ metadata حداکثر 512 KiB و حداکثر 1000 sibling است. DNS باید توسط resolver زیرساخت با timeout مناسب ارائه شود؛ اندازه response و timeout شبکه در cURL اعمال می‌شوند.
- فقط HTTPS به `huggingface.co`، بدون proxy ضمنی یا احراز هویت، با TLS validation و DNS IPv4 عمومی pin‌شده به cURL مجاز است. مسیر، شناسه، commit و نام فایل اعتبارسنجی می‌شوند؛ URL دلخواه کاربر پذیرفته نمی‌شود.
- redirect خودکار خاموش است؛ حداکثر سه انتقال کنترل‌شده روی همان دامنه پذیرفته می‌شود. انتقال به CDN/Xet/LFS خارجی عمداً مسدود است؛ ممکن است حتی برخی فایل‌های کوچک LFS در MVP قابل دریافت نباشند. در این حالت خطا نمایش داده می‌شود، نه دانلود ساختگی یا دورزدن دسترسی.
- قبل از دانلود اندازه اعلام‌شده، تعداد، سهمیه حساب/پروژه و فضای آزاد دیسک بررسی می‌شود؛ حین انتقال سقف بدنه و زمان و وضعیت لغو کنترل می‌شود. قبل از commit، سهمیه و لغو دوباره بررسی می‌شوند.
- Git blob SHA-1 (شامل پیشوند Git) یا LFS SHA-256 با metadata همان commit تطبیق داده می‌شود؛ SHA-256 محلی نیز برای تشخیص تغییر فایل ذخیره‌شده نگهداری و هنگام خواندن بررسی می‌شود. این کار یکپارچگی با منبع را می‌سنجد، نه اعتبار علمی، مجوز حقوقی یا بی‌ضرربودن محتوا.

### ذخیره‌سازی و یکپارچگی

دو جدول افزایشی `workspace_dataset_imports` و `workspace_hub_rates` به هر دو schema اضافه شده‌اند؛ جدول/ستون موجود حذف یا تغییر داده نمی‌شود. اولی شامل مالک، project، شناسه Hub، commit، fingerprint، وضعیت، اندازه و فراداده فایل است؛ محتوای فایل در آن وجود ندارد.

فایل‌ها در `storage/datasets/{import-id}/{index}.data` با دایرکتوری 0700 و فایل 0600 ذخیره می‌شوند. نام خارجی هیچ‌وقت مسیر فیزیکی مقصد نیست؛ فایل موقت بعد از اعتبارسنجی با rename اتمی منتشر می‌شود. manifest فقط برای نمایش/API یا اجرای Python از دیسک ساخته می‌شود. namespace منطقی `datasets/{import-id}/{original-path}` در tree دیده می‌شود. اگر پروژه از قبل فایل معمولی در `datasets/` داشته باشد، پیش از اولین import باید نام آن را تغییر دهد؛ داده قدیمی خودکار جابه‌جا یا حذف نمی‌شود.

فایل‌های واردشده در ویرایشگر فقط‌خواندنی‌اند؛ برای تبدیل داده از Python خروجی دیگری بسازید. تغییر موقت فایل داخل sandbox نسخه اصلی دیسک را عوض نمی‌کند. محتوای دیتاست در snapshot یا خروجی ذخیره‌شده برنامه/صف DB تکرار نمی‌شود؛ صف runner ورودی‌ها را در `RUNNER_DB.inputs` با دسترسی خصوصی spool می‌کند و پس از لغو یا پایان حذف می‌کند. برای ارتقای runner ابتدا صف را تخلیه کنید و backup صف و دایرکتوری ورودی را سازگار بگیرید.

Python فایل را با همان مسیر نسبی workspace، مثلاً `pandas.read_csv('datasets/<import-id>/Iris.csv')`، می‌خواند. شبکه sandbox همچنان بسته است؛ بسته `datasets` یا `huggingface_hub` داخل محیط دانشجو نصب نشده و لازم نیست. تصویر و نسخه scientific profile تغییر نکرده‌اند.

دانلود فایل‌به‌فایل با POSTهای کوتاه انجام می‌شود و به worker دائمی تازه نیاز ندارد. بستن صفحه دانلود را تا درخواست ادامه متوقف می‌کند؛ ادامه فقط پیش از انقضای 120 ثانیه ممکن است. لغو session را قفل نمی‌کند و callback انتقال آن را بررسی می‌کند؛ نتیجه نهایی با شرط state از بازنویسی لغو جلوگیری می‌کند. پس از انقضا، درخواست بعدی حساب رکورد را failed و فایل‌های موقت را با قفل پاک می‌کند. همان مجموعه فایل/commit به همان import برمی‌گردد؛ فایل قبلاً واردشده در مجموعه متفاوت نیز دوباره دریافت نمی‌شود. retry پس از لغو/خطا شناسه تازه و کنترل سهمیه تازه دارد.

پاک‌سازی پیش‌دستانه فایل‌های رهاشده پس از crash، prune تاریخچه 100تایی و حذف دائمی import رابط خودکار ندارند؛ نگهداری اپراتور لازم است. فایل موفق، مانند پروژه حذف نرم، تا سیاست حذف دائمی جزو سهمیه است. هیچ filesystem خارج از storage مجاز پروژه یا mount میزبان در اختیار Python قرار نمی‌گیرد.

### آزمون‌ها و نیازمندی استقرار

برای تکرار آزمون واقعی:

```sh
PHP_BIN=php NOVENTIX_HF_LIVE_TESTS=1 python3 -m unittest discover -s tools -p 'test_*.py' -q
node --check public/assets/workspace.js
php -l src/datasets.php
git diff --check
```

نتیجه اجرای نهایی مجموعه آزمون: **177 آزمون، 172 PASS، صفر FAIL و 5 آزمون container با وضعیت NOT TESTED/skip**. بررسی syntax فایل‌های PHP و JavaScript و `git diff --check` نیز PASS است.

آزمون‌های live بدون متغیر opt-in اجرا نمی‌شوند تا CI عادی به شبکه خارجی وابسته نباشد. fixture واقعی `scikit-learn/iris` از Hub گرفته می‌شود؛ فایل‌های fixture آزمون پس از اجرا پاک می‌شوند. آزمون‌های محلی runtime و auth mock نیستند: PHP HTTP واقعی، SQLite واقعی و فایل واقعی روی دیسک استفاده می‌شوند.

| مورد | شواهد این اجرا |
|---|---|
| جست‌وجو، جزئیات و دریافت واقعی Iris.csv | PASS، API رسمی بدون توکن |
| فایل در tree/API، دانلود خصوصی و manifest معتبر runner | PASS، محتوا با CSV دارای 150 ردیف بررسی شد |
| سهمیه پروژه، count، سقف response، فایل نامعتبر و checksum | PASS؛ فایل خراب ذخیره موفق نمی‌شود |
| دو مالک، کاربر ناشناس و CSRF | PASS، درخواست HTTP واقعی |
| لغو پیش از انتقال، retry، expiry و duplicate | PASS؛ race لغو وسط انتقال در محیط چند worker NOT TESTED |
| خطای HTTP منبع و مقصد غیرمجاز | PASS؛ قطع واقعی شبکه/timeout عمدی NOT TESTED |
| spool صف و عدم ذخیره محتوای دیتاست در DB | PASS، به‌همراه شکست بسته در checksum ورودی صف |
| اجرای دیتاست در container واقعی Python/gVisor | NOT TESTED؛ Docker/runsc و سرور ثبت‌شده موجود نیست |
| UI بصری/موبایل و MySQL واقعی | NOT TESTED؛ بررسی JS/PHP و schema موجود جای این آزمون‌ها نیست |

استقرار به PHP 8.2+ با cURL، mbstring و PDO موتور فعلی، CA bundle معتبر، DNS IPv4 و خروجی HTTPS به Hub نیاز دارد. سرور باید بتواند مستقیم به Hub وصل شود؛ proxy ضمنی محیط نادیده گرفته می‌شود. document root حتماً `public/` باشد؛ `storage/` نباید از وب قابل سرو باشد. storage خصوصی باید پایدار، قابل نوشتن برای PHP، دارای ظرفیت و backup هماهنگ با DB باشد؛ در چند instance از filesystem مشترک با flock معتبر و DB مشترک استفاده کنید. timeout reverse proxy/PHP-FPM متناسب با گام شبکه حداکثر حدود 20 ثانیه تنظیم شود. هیچ token جدیدی نیاز نیست. برای اجرای Python همان runner ایزوله، TLS و تنظیمات قبلی لازم است؛ اتصال Hub، استقرار runner را جایگزین نمی‌کند. تولید و آزمون واقعی container باید روی سرور ثبت‌شده انجام شود.

## محدودیت‌های باقی‌مانده

ویرایشگر فعلی textarea واقعی با شماره خط، Tab و میانبر ذخیره است؛ syntax highlighting، autocomplete، debugger و notebook ندارد. پوشه/فایل CRUD، CSV/JSON، دانلود و ZIP در کد یکپارچه‌اند ولی تأیید عملکرد HTTP و موبایل نیازمند محیط مناسب است. مدیریت حذف دائمی/پاک‌سازی تاریخچه، تاریخچه نسخه‌های کامل فایل، حذف تک‌فایل الگو از فرم مدیر و بارگذاری مستقیم داده از URL پیاده‌سازی نشده‌اند. خروجی اجرا فقط با دکمه ذخیره خروجی نگهداری می‌شود. اجرای کد تا استقرار و تأیید سلامت runner غیرفعال می‌ماند و پیام صریح نشان داده می‌شود؛ خروجی ساختگی ارائه نمی‌شود.
